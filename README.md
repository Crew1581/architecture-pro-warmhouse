### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать и выключать отопление в своём доме через веб-клиент.
- Сервер формирует команду для реле отопления.
- У пользователя нет возможности для самостоятельного подключения устройства.

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру по каждому датчику в интерфейсе.
- Монолит опрашивает датчики температуры и внешний сервис по HTTP и обновляет значения в БД.
- Исторические значения сохраняются, что позволяет строить графики.

### 2. Анализ архитектуры монолитного приложения

| Аспект | Значение |
| ------ | -------- |
| Язык | Go 1.21 (Gin, pgx) |
| Хранение | PostgreSQL 15 (общая схема `sensors`) |
| Развёртывание | Один контейнер, остановка ⇒ даунтайм всей системы |
| Взаимодействие | Синхронный REST JSON; опрос датчиков/внешнего API блокирует обработку |
| Масштабирование | Возможна только горизонтальная репликация всего монолита |

### 3. Определение доменов и границы контекстов

| Домен | Краткое описание | Текущий статус |
| ----- | ---------------- | -------------- |
| **Heating Control** | Команды управления отоплением | Реализован в монолите |
| **Sensor Monitoring (Телеметрия)** | Приём, хранение и показ показаний датчиков | Часть вынесена в telemetry-service |
| **Device Management** | Регистрация устройств, изменение состояния | Реализован в devices-service |
| **Scenario / Automation** | Сценарии умного дома | Планируется |

*Heating Control Context* и *Sensor Monitoring Context* реализованы одним репозиторием и общей БД.

### **4. Проблемы монолитного решения**

- Низкая масштабируемость: нагрузка на чтение телеметрии и выполнение команд по устройствам растёт неравномерно, но разделить сервисы невозможно.
- Даунтайм при деплое: обновление требует перезапуска всей системы.
- Сложность добавления новых типов устройств — нужно менять и пересобирать монолит.
- Риск блокировки: долгие HTTP-запросы к датчикам/внешнему API.
- Единая БД → высокий уровень связности, трудно внедрять разные модели хранения.
- Монолит мешает вовлечению партнёров-производителей устройств: необходим единый API-шлюз и механизм подключения.
- Отсутствует полноценная система аутентификации и авторизации, что затрудняет масштабирование и интеграцию с внешними сервисами.

Если оставить всё как есть, цели по росту количества домов и модулей выполнены не будут.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
